Para cubrir transversalmente **Patrones Distribuidos**, **Datos/Eventos** y **Observabilidad/Plataforma**, el escenario ideal es un dominio que requiera consistencia eventual, transacciones multi-paso con compensaciones y alta concurrencia.

---

### Temática recomendada: Sistema de Logística y Fulfillment de Envíos ("FastDrop")

Un flujo de fulfillment de e-commerce donde se procesa una orden de entrega que involucra tres dominios acoplados por negocio pero desacoplados técnicamente:

1. **Warehouse / Inventory Service:** Reserva stock físico en un centro de distribución.
2. **Dispatch / Delivery Service:** Asigna conductor/ruta y genera la etiqueta de envío.
3. **Notification / Tracking Service:** Actualiza el estado al cliente y emite telemetría de eventos.

---

### Mapeo de Requisitos e Implementación Técnica

#### 1. Patrones Distribuidos y Concurrencia (Fase 2)

* **Saga Pattern (Coreografiada o con Orquestador liviano):**
* Flujo exitoso: `OrderPlaced` $\rightarrow$ `StockReserved` $\rightarrow$ `DeliveryScheduled` $\rightarrow$ `OrderReadyForPickup`.
* Flujo de compensación (Rollback): Si falla la asignación de transporte (ej. sin flota disponible), se emite `DeliveryFailed`, lo que dispara la compensación en Warehouse (`CancelStockReservation`) y revierte el estado a `OrderCancelled`.


* **Transactional Outbox Pattern:**
* Al actualizar el estado de una orden en PostgreSQL, se escribe simultáneamente en una tabla `outbox_events` dentro de la **misma transacción relacional** (`@Transactional`).
* Un relay asíncrono (usando Debezium vía Change Data Capture o un worker con polling y bloqueo pesimista `SELECT ... FOR UPDATE SKIP LOCKED`) lee la tabla y publica a Kafka/RabbitMQ sin riesgo de dual-write.


* **Resiliencia (Resilience4j):**
* **Circuit Breaker & Fallback:** En llamadas a APIs externas (ej. geocodificación o validación de direcciones postales).
* **Retry con Backoff Exponencial:** Para reintentar publicaciones o conexiones transitorias.
* **Rate Limiter:** Para limitar endpoints públicos de tracking de envíos.


* **Virtual Threads (Java 21+):**
* Configurar `spring.threads.virtual.enabled=true` en Spring Boot 3.x.
* Diseñar endpoints I/O intensivos (consultas HTTP a pasarelas de tracking, lecturas a DB con JDBC bloqueante) aprovechando la planificación de Virtual Threads sobre los carriers sin agotar el pool de conexiones ni saturar memoria.



---

#### 2. Datos, Asincronismo y Eventos (Fase 3)

* **Broker de Mensajería (Kafka o RabbitMQ):**
* *Si elegís Kafka:*
* Tópicos clave: `warehouse.inventory-events`, `logistics.dispatch-events`, `orders.saga-commands`.
* Particionado por `order_id` o `warehouse_id` para garantizar ordenamiento estricto de eventos por entidad.
* Consumer groups independientes para tracking y analítica. Manejo de **DLQ (Dead Letter Queue)** y reintentos automáticos tras $N$ fallas.


* *Si elegís RabbitMQ:* Direct/Topic Exchanges con routing keys semánticas (`shipment.created`, `shipment.cancelled`) y TTL para mensajes reintentados.


* **Modelado en PostgreSQL:**
* Esquemas separados por bounded context (o bases independientes para simular microservicios reales).
* Columnas para concurrencia optimista (`@Version` en JPA) para evitar sobre-escritura en reservas de stock concurrentes.
* Índices parciales o B-Tree sobre estados no finalizados (`WHERE status IN ('PENDING', 'PROCESSING')`) para optimizar el worker del Outbox.


* **Estrategia de Caching (Redis):**
* **Cache-Aside Pattern:** Cachear el estado del tracking de envíos (`GET /shipments/{id}/tracking`) con un TTL corto (ej. 30 segundos).
* **Invalidación reactiva:** Consumir eventos del broker (`ShipmentMoved`, `ShipmentDelivered`) para expulsar la clave de Redis (`DEL shipment:{id}`) de forma proactiva.



---

#### 3. Observabilidad, Plataforma y Documentación (Fase 4)

* **OpenTelemetry (OTel):**
* OTel Java Agent o instrumentación con Micrometer Tracing.
* **Trazabilidad distribuida de punta a punta:** El trace context (`traceparent` header) debe propagarse desde el HTTP controller, pasar a través de las tablas del Outbox, viajar en los Kafka/RabbitMQ headers y recuperarse en el consumidor.
* Correlación de logs: Cada línea de log en JSON debe incluir `trace_id` y `span_id`.


* **Kubernetes (K8s) Patterns:**
* **Probes:** `livenessProbe` (detecta deadlocks), `readinessProbe` (verifica conexión a PostgreSQL y broker) y `startupProbe` para arranque inicial.
* **Configuración desacoplada:** `ConfigMap` para variables generales y `Secret` para credenciales de base de datos/broker.
* **Despliegues y recursos:** Definir `resources.requests` y `resources.limits` ajustados para la JVM, y manifests para simular un despliegue Blue/Green o Rolling Update.


* **Documentación de Arquitectura:**
* **Modelo C4 (en Structurizr DSL o PlantUML/Mermaid):**
* *Nivel 1 (Context):* Usuarios (clientes, choferes), sistema FastDrop y sistemas externos (proveedores de mapas, pasarelas).
* *Nivel 2 (Containers):* Servicios backend en Java, base de datos PostgreSQL, cluster de Kafka/RabbitMQ, Redis cache y Grafana/Prometheus.
* *Nivel 3 (Components):* Diagrama interno de un servicio (Controllers, Handlers de Saga, Repositorios, Outbox Publisher).


* **ADRs (Architecture Decision Records):**
* *ADR-001:* Adopción de Transactional Outbox vs 2PC (Two-Phase Commit) para consistencia de datos.
* *ADR-002:* Elección de Saga Coreografiada vs Orquestada para el flujo de reservas de envío.
* *ADR-003:* Uso de Virtual Threads frente a programación reactiva (WebFlux) para simplificar el modelo de concurrencia.

# ADR-001: Implementación del Patrón Transactional Outbox para Publicación Confiable de Eventos

* **Estado:** Aceptado
* **Fecha:** 2026-10-14
* **Decisores:** Equipo de Arquitectura e Ingeniería Backend
* **Contexto Técnico:** Java 21, Spring Boot 3.x, PostgreSQL 16, Apache Kafka

---

## 1. Contexto y Planteamiento del Problema

En el sistema de logística y fulfillment de envíos (**FastDrop**), los servicios (Warehouse, Dispatch, Tracking) necesitan persistir cambios de estado en sus bases de datos relacionales y notificar de inmediato a otros microservicios mediante eventos de dominio en Apache Kafka (por ejemplo, `StockReserved`, `ShipmentScheduled`).

El enfoque ingenuo de *Dual-Write* (escribir en la base de datos y luego invocar `kafkaTemplate.send()`) introduce fallos de atomicidad críticos:
1. Si la transacción en PostgreSQL hace commit exitoso pero el broker de Kafka no está disponible o falla la red, el evento se pierde definitivamente, dejando al resto del sistema en un estado inconsistente.
2. Si se invoca a Kafka primero y la transacción en PostgreSQL falla (rollback por violación de constraints, timeout, etc.), se emite un evento fantasma al clúster para un cambio que nunca existió.

El uso de transacciones distribuidas tradicionales tipo Two-Phase Commit (2PC / XA) no es viable: introduce bloqueos prolongados, reduce drásticamente el throughput, agrega un punto único de falla con el coordinador de transacciones y no cuenta con soporte nativo eficiente en brokers modernos como Kafka.

---

## 2. Decisiones Consideradas

* **Opción 1: Dual-Write con reintentos locales en memoria.**
* **Opción 2: Two-Phase Commit (2PC) / XA Transactions.**
* **Opción 3: Transactional Outbox Pattern con relay asíncrono (Polling Publisher).**
* **Opción 4: Transactional Outbox Pattern con Change Data Capture (CDC / Debezium).**

---

## 3. Decisión Aceptada

Se decide implementar el **Patrón Transactional Outbox (Opción 3 con evolución planeada a Opción 4)**:

1. **Escritura Atómica Local:** Cada servicio persistirá la entidad de negocio y el registro del evento en una tabla dedicada (`outbox_events`) dentro de la **misma transacción local de PostgreSQL** (`@Transactional`).
2. **Esquema de Outbox:**
   * `id` (UUID, PK)
   * `aggregate_type` (VARCHAR)
   * `aggregate_id` (VARCHAR)
   * `event_type` (VARCHAR)
   * `payload` (JSONB)
   * `trace_context` (JSONB / Map con `traceparent` de OpenTelemetry)
   * `created_at` (TIMESTAMPTZ)
   * `processed_at` (TIMESTAMPTZ, nullable)
3. **Mecanismo de Despacho (Fase Inicial):** Un worker asíncrono en segundo plano (`@Scheduled` con Virtual Threads) leerá eventos pendientes usando la sentencia SQL:
   ```sql
   SELECT * FROM outbox_events
   WHERE processed_at IS NULL
   ORDER BY created_at ASC
   LIMIT 100
   FOR UPDATE SKIP LOCKED;
